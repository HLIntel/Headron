# API Contracts and Integrations

Use explicit contracts across HTTP, JSON, webhooks, tools, agents, and services.

## Contract stack

```text
JSON Schema / OpenAPI / AsyncAPI
        ↓
runtime validation
        ↓
typed language model
        ↓
business logic
        ↓
side effect
```

## Choose the contract

| Interface | Contract model |
|---|---|
| REST/HTTP API | OpenAPI + JSON Schema |
| event/webhook | JSON Schema + event envelope |
| message stream | AsyncAPI + schema |
| MCP tool | JSON Schema input/output |
| internal typed API | language-native types + tests |

## Contract requirements
- version ownership
- compatibility rules
- required fields
- unknown-field policy
- size/depth limits
- error schema
- timeout semantics
- pagination semantics
- idempotency semantics
- auth semantics

## Versioning

Prefer additive changes when compatibility matters. Explicitly version breaking changes. Keep old readers/writers long enough to make the migration safe.

## Error contracts

Do not make callers infer failure from strings.

Prefer structured errors containing a stable machine-readable code, retryability, correlation/request ID, and safe human message.

## AI tools

LLM-generated arguments must be validated exactly like ordinary external API input. Do not treat model output as trusted because it was generated by your own model.
