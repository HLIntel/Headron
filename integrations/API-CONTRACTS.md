# API Contracts and Integrations

Use explicit contracts across HTTP, JSON, webhooks, tools, agents, and services.

**What enforces this page.** Boundary contracts are the one thing no single pack answers for:
`authority_classes/boundary` is deliberately empty and names what closes it instead. What a person
or agent should have at all, and the `never_by_default` list, is `atlas.yaml/developer_baseline`.

## Contract stack

```text
JSON Schema / OpenAPI / AsyncAPI
        ↓
runtime validation
        ↓
typed language model
        ↓
business logic
        ↓
side effect
```

## Choose the contract

| Interface | Contract model |
|---|---|
| REST/HTTP API | OpenAPI + JSON Schema |
| event/webhook | JSON Schema + event envelope |
| message stream | AsyncAPI + schema |
| MCP tool | JSON Schema input/output |
| internal typed API | language-native types + tests |

## Contract requirements
- version ownership
- compatibility rules
- required fields
- unknown-field policy
- size/depth limits
- error schema
- timeout semantics
- pagination semantics
- idempotency semantics
- auth semantics

## Versioning

Prefer additive changes when compatibility matters. Explicitly version breaking changes. Keep old readers/writers long enough to make the migration safe.

## Error contracts

Do not make callers infer failure from strings.

Prefer structured errors containing a stable machine-readable code, retryability, correlation/request ID, and safe human message.

## AI tools

LLM-generated arguments must be validated exactly like ordinary external API input. Do not treat model output as trusted because it was generated by your own model.

## Endpoints

An endpoint is a contract plus an operational boundary: REST/HTTP, webhook ingress, MCP remote,
health/readiness, metrics, callbacks, internal service, OpenAI-compatible model endpoint. Document
method, path, auth, schemas, timeout, rate limit, idempotency, pagination, retryability, side
effects, observability and versioning.

- Every retryable side effect has a defined idempotency model; agents and bots get explicit pagination budgets.
- Separate liveness, readiness and dependency health.
- A model endpoint's `base_url + model + auth_env + timeout + retry_budget` lives in provider configuration.

## Webhook ingress

A webhook turns an external event into an executable path: design it as security-sensitive
ingress, never as an ordinary endpoint.

```text
TLS -> capture raw body -> verify signature -> delivery metadata -> size / replay limits
    -> schema validate -> idempotency check -> enqueue bounded work -> acknowledge quickly
```

- **Signature first.** GitHub signs with `X-Hub-Signature-256` (HMAC-SHA256 over the ORIGINAL body,
  compared in constant time, secret never hardcoded); reject a missing or invalid signature before
  any expensive work. The runnable version is
  [examples/webhooks/github_verify.py](../examples/webhooks/github_verify.py).
  References: [validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries),
  [best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks).
- **Redelivery is normal.** Keep a retained event identifier and make every handler idempotent.
- **Never** trigger an irreversible operation from the handler, enqueue unbounded jobs, parse an
  unbounded body, trust a payload field before schema validation, or log secrets.
- Heavy processing belongs outside the request path. Every language adapter keeps the same order:
  raw-body verification, then schema validation, then bounded execution.
